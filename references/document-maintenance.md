# 文档定位与维护

## 目标判定

按以下优先级确认本任务的记录：

1. 用户本次明确指定的工作记录 URL。
2. 当前任务会话中曾成功创建或确认维护的工作记录 URL／document_id。
3. 本任务工作区中已保存的文档绑定信息。

先通过 `lark-doc` 读取实际文档，核对任务主题、主要内容及归属。不要把会话里引用的规范样例、其他业务文档或只有同名的文档当作本任务记录；标题和日期不能单独证明对应关系。

已有确定链接但文档读取失败、已删除或无权限时，报告原因并保留原绑定，不自动另建。多个候选或无法区分任务时，只询问缺少的目标信息。没有绑定且不确定是否已有记录时，按已安装的 `lark-drive` 搜索能力在用户资源中查找；只能找到候选后再读内容核对。搜索失败不等于没有记录，不能凭空查询或无结果页面宣布首次创建。

确认是首次记录时在 `my_library` 创建。用户明确要求另建时，新建并保留原文档；若明确作为独立快照，则后续默认继续维护原任务记录，除非用户指定切换到新文档。

## 保存任务绑定

成功创建或确认目标后，将下列最少信息保存到任务独占工作区，而不是技能仓库：

| 字段 | 用途 |
| --- | --- |
| task_key | 当前会话／任务的稳定标识；优先使用已知会话ID，不能猜造 |
| task_summary | 人可读任务主题，只作为辅助 |
| document_id、url | 后续精确定位原记录 |
| original_title、created_date | 保留原名称及首次创建日期 |
| last_revision | 上次观察或成功更新的版本，用于发现并发修改 |

可使用 `work-record-binding.json`，并在会话交付时返回文档链接。任务ID不可用时，保留任务工作区与会话中确认的URL，不用同名标题作为全局绑定键。绑定写入失败时交付已创建链接并说明本地记录缺口，不能因此重复创建。

## 增量维护

- 按 `lark-doc` 的 update 流程先读现状，保存需要的完整响应和 `reference_map`，建立块级修改计划。保持原文档名称和创建日期。
- 将新增事实并入对应事项行，刷新当前结果与成果；真正发生新的修改才增加迭代行。没有新增事实时返回同一链接及“无新增事实”，不重复追加内容。
- 保留历史迭代的时间、当时结论和证据；新的结论写入当前状态或新迭代，不将旧失败记录改成当时已通过。
- 原文档有旧开场或后续章节时，仅整理本次维护的文档。删除前检查其中是否有独有事实、证据或人工补充：与结果相关的未完成事实迁入对应状态表；有效材料保留在相关模块。移除冗余元说明和未来行动清单。
- 更新采用最新 block ID 的局部操作，尽量保留现有 block，保护资源 token、图片附件、引用、人工内容和未涉及的模块。整篇候选用于预检，不能据此整篇覆盖云文档。
- 读后发现 revision 变化时重读并合并；不凭过期绑定版本覆盖他人内容。警告、部分成功或超时先回读确认，修复同一对象，不重复追加或另建。

## 回读确认

核对更新位置、标题连续编号、表格状态、有效历史和资源保留。源码按本次快照逐字符比对。更新后仍是原 document_id 和标题，再保存新 revision。无法确认线上结果时报告“更新状态待核实”，不能把离线校验当作线上维护成功。
