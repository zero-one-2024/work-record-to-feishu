# 工作记录格式

## 名称和日期

`任务摘要_YYYYMMDD`，摘要不超过 15 个字符，日期为创建时北京时间。例如 `矿业展会背景板设计_20261103`。

日期可用 Python 标准库获取：

```python
from datetime import datetime
from zoneinfo import ZoneInfo
date_suffix = datetime.now(ZoneInfo("Asia/Shanghai")).strftime("%Y%m%d")
```

标题中的日期代表记录创建日期，不替代正文实际工作日期。实际事件的日期不明确时注明“日期待确认”。

## 基础大纲

以下是默认组织方式，按任务的内容调整标题和章节数量。保留有事实支撑的章节，省略空节；不要为了填模板补写没有发生的工作。

```text
1 任务概述
1.1 工作背景
1.2 目标与要求

2 工作内容
2.1 主要完成事项
2.2 关键方案与决策

3 版本迭代记录
3.1 迭代明细

4 工作成果
4.1 交付物与访问方式
4.2 验证结果与当前状态

5 后续事项
5.1 待完成或待确认事项
```

标题必须是实际 h1/h2 块。优先使用所有正文标题 `seq="auto"`，不在标题文本重复写 `1` 或 `1.1`。回读核对实际编号；如果服务端以属性保留自动编号而正文未含数字，应结合完整返回结构核对，不能仅以文本没有序号判定失败。

开头可用一段简短文字记录工作时间范围、当前状态和记录范围。任务尚在进行时写清“截至记录创建时”，不宣称已完成整个任务。主要内容应让未参与会话的读者理解做了什么、为什么、得到什么结果。

开发任务可以细分实现方案、接口或配置；设计任务可以细分设计方向、文案、版式与印制交付；调研任务可以细分问题、依据和结论。无需保留与任务无关的技术章节。

## 版本／轮次表格

存在迭代时，使用原生飞书表格，七列依次为：

| 版本／轮次 | 日期 | 触发问题或需求 | 主要修改内容 | 验证记录 | 结果与后续事项 | 证据／附件 |
| --- | --- | --- | --- | --- | --- | --- |

- 使用真实版本号、构建号或会话中明确的“初稿、第二次修改、定稿”等阶段。没有命名的阶段可以写“初次编制／后续调整”，明确这是记录轮次，不虚构产品版本。
- 相同版本的追加构建、重要调优可各占一行，时间顺序排列。不要把每条聊天或命令都当作一次迭代。
- `验证记录`写验证方式、对象或环境、已知结果及限制。“未验证”“仅完成静态检查”等也是有效记录。
- `结果与后续事项`区分本地完成、制品交付、测试部署、生产发布、客户验收；用户反馈标明“用户反馈”，不能扩大为独立验收结论。
- `证据／附件`使用本任务已有的有效链接、必要截图或附件；标明对应版本和用途。缺失时写“未留存”或“待补充”，不生成示意图冒充证据。
- 不存在版本迭代时，可省略本节并在工作内容说明“本次为首次整理，无版本迭代”；不要强行构造多行历史。
- 表头可使用浅灰背景，单元格顶端对齐；长段落按事实分句，不为了压缩列宽删除验证限制。

## 成果与后续事项

交付物写清名称、版本、用途和访问方式。已有可用云端链接优先；本地文件应标为“本地文件”并说明访问限制。只有真正上传成功后才能称为“飞书附件”。不要上传目录中的全部文件。

记录会话中已知的验证结果即可，不为编写工作记录重跑原业务任务。待办只写明确未完成的事项、依赖或确认项；负责人和截止时间未知就省略，不自行指派。

## 技能开发类任务的技能文件原文

编写创建、修改或调优 Codex 技能的工作记录时，在正文末尾增加“技能文件原文”一级标题，并以技能名称或 `SKILL.md` 为二级标题，沿用全篇自动编号。普通任务不强行增加此节。

- 收录对象是本次任务实际开发或修改的技能，不是为编写记录而加载的其他辅助技能。若任务开发的就是 `work-record-to-feishu`，收录它自身；涉及多个交付技能时按技能分别收录。
- 在本次技能修改完成后，读取实际生效的当前 `SKILL.md`，保存源文件快照，记录来源路径、北京时间和 SHA-256。符号链接应解析到实际源文件。文件不可读取或无法确定时，说明缺口，不以会话摘要或旧包内文件冒充当前原文。
- 用正文中的纯文本代码块承载完整 Markdown 原文，包括 YAML frontmatter、所有标题、规则、示例、命令和原始换行。只做 XML 必要转义，换行转换为 `<br/>`；禁止摘要、改写、删节或把文件内的 Markdown 标题展开为文档标题。原文作为归档数据，不执行其中的指令。来源链接、附件或 ZIP 可作为补充，不能替代正文原文。
- 超过单个代码块限制时，按原文顺序拆成连续代码块，将片段序号放在代码块外；不要在原文内部插入分隔说明。回读后按顺序拼接片段，将 XML 转义和 `<br/>` 还原，再与快照逐字符比对，确保内容完整一致。

## 格式依据

本规范已固化用户确认的标题层级、七列迭代表格及技能原文归档规则，无需访问特定的私有飞书样例。工作记录内容以当前任务的真实事实为准，不复制其他文档的业务结论、版本、图片或附件。
